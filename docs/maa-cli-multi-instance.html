maa-cli 多实例肉鸽 · 配置复用 / 隔离 / 集合器基于 v0.7.5 官方文档 + 本机实测 + canary 并发实证

回答三个问题：①一个 CLI 能控几个模拟器 ②多次运行会不会互相污染 ③每次运行怎么带配置——以及"肉鸽配置集合器"该怎么建。

① 一个 maa-cli 能控几台模拟器？

运行层面：一次 maa run/roguelike 只驱动「一台」设备（由 -a 设备地址 决定）。要同时控制 8 台 = 跑 8 个 maa-cli 进程，每个进程负责一台。

每个进程是独立、可并发的，但必须做三件事隔离（否则会互相污染）：

维度机制结论
连接参数每个进程用自己设备的 -a 127.0.0.1:<port> 每次传入 天然隔离——不同端口就是不同模拟器
运行状态目录每个进程设独立的 MAA_STATE_DIR（如 state/idx0、state/idx34） 不隔离 = asst.log / 资源缓存放一起，多进程并发时日志互串（canary 实证：同目录=后占者整窗丢日志）
任务/资源任务文件 <task> 与 profile 按机器分别指定 文件只读加载，不互相覆盖
# 示例：同时开 3 台 MAA_STATE_DIR=D:\maa\state\idx0 maa.exe run rogue_mizuki -a 127.0.0.1:16384 MAA_STATE_DIR=D:\maa\state\idx2 maa.exe run rogue_sami -a 127.0.0.1:16448 MAA_STATE_DIR=D:\maa\state\idx34 maa.exe run rogue_sarkaz -a 127.0.0.1:16452

② 多次运行会不会「配置污染」？会不会变回默认？

关键结论：maa-cli 每次运行都是「临时填入参数」进入核心，跑完不改配置文件。它不是"用完重置成默认"，也不是"永久改配置"——是「无状态加载」模型。

每次运行的完整流程（一次性生效，不写回）：
1. 命令行/环境变量给出覆盖项（-a 设备、-p profile、-v 等）
2. maa-cli 读 profiles/<name>.toml → 得到连接参数（adb/地址/resource 等）
3. maa-cli 读 tasks/<name>.toml → 得到任务链（StartUp/Roguelike + 参数）
4. 合入 core 参数（theme/mode/difficulty/core_char/roles/use_support/investment_enabled…）
5. 启动 MaaCore 实例，连 -a 指定的那台设备 → 执行 → 结束。
没有「写回」步骤：配置文件始终保持你上次编辑的状态；命令行 -a、--difficulty 等都是一次性覆盖。
问答
每次运行结束会变回默认吗？不会。配置文件的当前内容就是下次运行的默认——你写进 rogue_mizuki…toml 的难度/阵容会一直在，直到你改文件。
会不会被别的实例污染？只有一种真实污染源：共用 MAA_STATE_DIR。多个进程同 state 目录 → asst.log 互串、缓存冲突。用 state/每实例一目录 即可根治。
多个任务文件会互相覆盖吗？不会。每个 tasks/*.toml 是独立文件，各管各的。
资源/热更新会不会串？资源（皮肤、活动等）按 resource/global=YoStarJP 加载，共享只读，绝大多数情况不冲突。

③ 每次运行带什么配置？三层来源

层来自哪示例作用范围
全局默认profiles/<default>.tomladb 路径、默认设备地址、global_resource整台机器
任务文件tasks/<name>.tomltheme/mode/difficulty/core_char/roles/investment…单个任务
命令行覆盖-a / -p / --mode / --difficulty …本次跑哪台、覆盖难度本次运行（一次性）
三者合并顺序：命令行覆盖 > 任务文件 > profile。跑完不写回，所以默认永远是你文件里的内容。
要"换配置跑"，就是 编辑对应 task 文件或命令行加参数，别无他法——这既是机制也是优点。

④ 肉鸽「配置集合器」怎么建

你想要的"集合器"本质上是一个 多实例配置库 + 启动入口。maa-cli 已给了骨架（profiles/ + tasks/ + MAA_STATE_DIR），需要补的是一层管理。推荐目录结构：

%APPDATA%\loong\maa\config\ ├── profiles\ # 连接配置（可选：每台模拟器一个，含 adb/地址） │ └── default.toml ├── tasks\ # ★ 肉鸽任务文件（每套打法一个） │ ├── rogue_mizuki__wsh.toml # 水月·维什戴尔阵容 │ ├── rogue_sami__max.toml # 萨米·MAX │ ├── rogue_sarkaz__max.toml # 萨卡兹·MAX │ └── … └── state\ # ★ MAA_STATE_DIR（每实例一目录，防污染） ├── idx0\ ├── idx2\ └── idx34\

启动一个实例 = 固定组合「设备地址 + 任务文件 + 独立 state 目录」。可以用简单脚本做「集合器入口」：

# rogue-launch.ps1（概念示例）：按"实例名"拉起对应组合 # 用法: .\rogue-launch.ps1 idx0 rogue_mizuki__wsh param($Device, $Task) $ports = @{ idx0="127.0.0.1:16384"; idx2="127.0.0.1:16448"; idx34="127.0.0.1:16452" } $env:MAA_STATE_DIR = "D:\MAA-CLI\state\$Device" # 每实例独立 state & D:\MAA-CLI\dist\maa.exe --batch run $Task -a $ports[$Device] -p default
  • 多实例同时跑：进程间靠「不同设备端口 + 不同 MAA_STATE_DIR」隔离，互不干扰。
  • 换一套打法：改/加 tasks/*.toml，不影响别的实例（因为 state、设备都已分开）。
  • 回滚：任务文件是纯文本，git 管理即可。

注意：Phantom 傀影 主题 core 不支持难度参数（Difficulty is not valid for Phantom theme, ignored，dry-run 实测），所以傀影的"难度3"无法通过 CLI 表达，集合器里也只能按"忽略难度"或另用开局收藏品方式处理。

⑤ 一个 CLI 能控几个？—— 一句话总结

一个进程 = 一台模拟器；8 台 = 8 个进程（每进程独立 -a + MAA_STATE_DIR）。 配置不会死后变成默认，它只读加载、按「命令行 > 任务文件 > profile」合并，跑完不写回。 唯一会污染的是共用 state 目录，用「每实例一目录」根治。
